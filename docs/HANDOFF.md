### IPC and hotkey parser (track B)

The Darwin branches of `Sources/VestalCore/IPC.swift` compile against the macOS 14.4 SDK and CI runs `IPCTests` on macOS; the runtime behaviour below is untested here.

- Sockets are made without `SOCK_CLOEXEC` (Darwin has none, nor `accept4`), then `FD_CLOEXEC`, `O_NONBLOCK` and `SO_NOSIGPIPE`: a tiny window where a concurrent exec could inherit one (Foundation's `Process` closes stray descriptors anyway).
- `sun_len` is set to `sizeof(sockaddr_un)`; the kernel uses the length passed. `getpeereid` on both ends: the client should see the listener's uid. The socket is chmod 0600 after bind (Darwin ignores `fchmod` on sockets); the per-user temp directory is 0700 anyway.
- `flock` on APFS: two `open()`s of the same file in one process conflict (the tests rely on it).
- The socket directory comes from `confstr(_CS_DARWIN_USER_TEMP_DIR)` since the IPC review (`2ae89cb`). Look for: step 3's `nix develop` check; `ls -l $(getconf DARWIN_USER_TEMP_DIR)vestal-$(id -u).sock*`.
- macOS socket buffers are 8KB, so large replies take the partial-write path far more often than on Linux (covered by tests that CI runs on macOS).

## Judgment calls

Decisions made without the owner, and why.

- **IPC review: the socket's directory.** On macOS it comes from `confstr(_CS_DARWIN_USER_TEMP_DIR)`, not `NSTemporaryDirectory()`, which follows `$TMPDIR`: a `nix develop` shell sets its own, so `vestal status` there looked for another socket than the launch agent's, and a `vestal` started there became a second instance. On Linux without `XDG_RUNTIME_DIR` (cron, a bare ssh session) the socket goes in `/run/user/<uid>` when that is a real directory of the user's, where a session or service with systemd's usual value has it; the temporary directory stays the fallback that clients and a starting server also check. PLAN "Process model" says so now.
- **IPC review: a hotkey that doesn't parse** is an `invalidValue` warning in check-config and `vestal status` and registers nothing. CONFIG.md says which keys need cmd, ctrl or alt.

- **Phase 6: a resident core in VestalCore** (`Resident`). Commands, show and hide, the hotkey, reloads and `status` are decided there and tested on Linux with a fake window, registrar and watcher, and once end to end over a real socket. The platform supplies `ResidentSurface` (the window), `HotkeyRegistrar` (Carbon) and `ConfigWatcher` (DispatchSource); Linux has no watcher yet, and a Linux UI or a headless `vestal daemon` (phase 8) can plug into the same place. `AppConfig` is gone: the resident holds the config in effect.
- **Phase 6: the socket comes before the window.** main.swift binds it (`CLI.claim`) before AppKit starts, so a second `vestal` never opens a window; commands that arrive in between wait in `ResidentInbox`. Bare `vestal` with an instance running sends `show` and exits 0. `vestal daemon` exits 0 with `already running (pid N)` when the running instance reports the same `BuildInfo.build` ("0.3.0 (abc1234)"); another build is asked to `quit` and replaced once it lets go of the lock (up to 5s). A dev build ("dev") and a Nix build replace each other; two dev builds don't. When the socket is taken but nothing answers (an instance starting or quitting), both look again for about a second and never start one (IPC review).
- **Phase 6: `hide` with no instance exits 1** (`vestal: not running`), as `reload`, `status` and `quit` do (the DESIGN contract); only `show` and `toggle` start one. Commands print nothing on success (skhd, activation); errors go to stderr, `status` to stdout. Extra arguments are a usage error (exit 2); a `-psn_…` argument from LaunchServices is ignored.
- **Phase 6: starting from `show`/`toggle` uses `NSWorkspace.openApplication`** from a bundle, not `/usr/bin/open`, which doesn't pass the caller's environment, so `$VESTAL_CONFIG` still carries over (the whole environment is passed). No arguments: the new instance comes up shown. Outside a bundle the binary starts itself, detached, as before.
- **Phase 6: hide ends with `NSApp.hide`** after `orderOut`, so AppKit gives the focus back to the app that had it (TASKS' "return focus to the previously active app", also right when the user switched apps meanwhile); show calls `NSApp.unhide` first. A show during the fade-out cancels the rest of it (a counter), so fast toggles never leave a blank window.
- **Phase 6: a reload rebuilds the dashboard** (a new `DashboardModel` and hosting view in the same window; the old model drops its observer and tickers) only when the config changed; the runtime keeps unchanged sources' data. `vestal reload` answers at once with the result; SIGHUP and the file watcher reload 300ms after the last event of a burst. A file that can't be read or parsed keeps the running config: `vestal reload` exits 1 with the error, and `status` lists `reload: ... the previous config stays in effect` until a reload works. Deleting the file (without `$VESTAL_CONFIG`) goes back to the defaults, as a start without it would.
- **Phase 6: the watcher** covers the file and its directory, without attribute events (reading the file may touch its access time), and is opened again after every reload so it follows a replaced file. A directory that doesn't exist yet is not watched.
- **Phase 6: the hotkey** is registered at start, and again on a reload only when `hotkey` changed or the last registration failed. It toggles. A refused registration is a `status` warning, and `status.hotkey` is then nil.
- **Phase 6: signals** (coordinator's design): a no-op C handler instead of `SIG_IGN`, which children inherit across exec, plus the DispatchSource. Finding on Linux: libdispatch installs its own handler the first time a signal gets a source (`_dispatch_muxnote_signal_block_and_raise`: it blocks signals in the thread that got one and raises it again on its manager thread, where a signalfd reads it). It does that once per process, so after `SignalWatch.cancel()` a second watch of the same signal never fires on Linux. The app keeps one watch per signal for its lifetime; `SignalTests` watches each signal once and runs on Linux here and on macOS in CI.
- **Phase 6: commands are killed at quit.** `CommandRunner` keeps the pids of its running children; `AppRuntime.shutdown()` SIGKILLs them all at once (the runtime's and the privacy toggle's), since the SIGKILL that follows a cancelled run's SIGTERM comes a second later, after the app is gone. Supersedes the phase 4 judgment call on `shutdown()`.
- **Phase 6: `status`** lists the config's sources by name, then the host health jobs as `host:<name>` (type `health`); ages read `42s`, `5m`, `3h 12m`, `2d 4h`.

- **IPC (track B): macOS ignores `XDG_RUNTIME_DIR`** (`IPC.usesRuntimeDirectory == false`): a shell-only value would otherwise put the shell and the launch agent on different sockets and allow two instances. Linux follows PLAN, with the temp path as a second candidate that clients try and a starting server checks.
- **IPC (track B): an advisory lock `<socket>.lock` (flock)**, held from `start()` to `stop()`. The connect probe stays (a live socket means `.alreadyRunning`, a dead one is removed and bound), but only the lock holder may remove and bind: that closes two races, two instances starting together, and on Darwin a live server whose full accept queue refuses connections looking stale. The kernel drops the lock when the process dies, so nothing goes stale; it is not a pid file, and it is never deleted.
- **IPC (track B): socket upkeep.** Every 60s the server touches both files (temp cleaners go by age), binds the socket again if it was deleted and takes the lock file again if that was. If another instance of ours has taken the path over, the server stops and the app quits (`onLostOwnership`).
- **IPC (track B): only the owner's processes.** The socket is 0600 (on Linux through `fchmod` before bind, so there is no window); both ends check the peer's uid (`SO_PEERCRED` on Linux, read as a 12-byte tuple since Glibc's Swift module lacks `struct ucred`; `getpeereid` on Darwin). The server hangs up on other users; the client refuses another user's server; another user's lock file or stale socket is refused. This only matters for the shared-temp-directory fallback on Linux.
- **IPC (track B): protocol details.** One request per connection; a request without a newline counts at EOF; commands are exact lowercase after trimming; requests are at most 256 bytes; more than 32 clients at once are told `busy`; the server allows 2s for sending and taking a reply and 4s for the handler, under the client's 5s. The `status` payload is a typed `IPCStatus`, and new fields go in as optionals.
- **Hotkeys (track B): letters, digits, space and escape need cmd, ctrl or alt**; shift alone doesn't count. The hotkey is global, and a bare `a` or `space` would be taken from every app. `f1`-`f20`, `home` and `end` may stand alone (F3 on swift, Home on mantle). Letters and digits are ANSI key positions: on a non-US layout `cmd+a` is the key labelled A on a US keyboard (translating through `UCKeyTranslate` would fix it).

- **Phase 7 (track C): `bin/vestal` is a `makeBinaryWrapper` wrapper, not a symlink.** macOS finds `Bundle.main` (and with it the Info.plist and the TCC identity) from the path the process was started with; the wrapper execs `Applications/Vestal.app/Contents/MacOS/vestal` by absolute path, so `show`/`toggle` launch the bundle.
- **Phase 7 (track C): Info.plist** is generated with `lib.generators.toPlist { escape = true; }` and parsed by Python's `plistlib` in the `info-plist` check (no `plutil` on Linux). Beyond TASKS' keys: `CFBundleVersion`, `CFBundleDisplayName`, `CFBundleDevelopmentRegion`, `CFBundleInfoDictionaryVersion`, `NSHighResolutionCapable`, `NSPrincipalClass`, and a `PkgInfo` file. No icon yet. The version lives only in `BuildInfo.version` (`package.nix` reads it). `buildCommit` is `self.shortRev or self.dirtyShortRev`, so a dirty tree shows `<hash>-dirty`.
- **Phase 7 (track C): `settings = { }` writes no file** (the Home Manager convention); other settings get `version = 1` unless set.
- **Phase 7 (track C): the launch agent** runs `[ <bundle exe> "daemon" ]` with `RunAtLoad`, `KeepAlive = { SuccessfulExit = false; }` (`vestal quit` and "already running" exit 0 and must not be restarted; with `KeepAlive = true` the second would respawn every 10s), `ProcessType = Interactive`, a `PATH` with the Nix profile directories, `XDG_CONFIG_HOME` = `xdg.configHome`, and output to `~/Library/Logs/vestal.log`. The Linux systemd user service is only defined when `package.supportsDaemon` (false until the Linux daemon exists).
- **Phase 7 (track C): `signingIdentity`** (darwin only, ignored on Linux so one config serves both) copies the app to `~/Applications/Vestal.app` at activation, signs it with nixpkgs' `codesign_allocate` and `--timestamp=none`, swaps it in by renames so a failure never leaves a half-deleted app, stamps it (`$XDG_STATE_HOME/vestal/signed-app`) to skip unchanged builds, and restarts the agent when it changed. A failed signing never fails activation: a copy signed with an identity stays; otherwise this build is installed ad hoc (and as built if even that fails). With `signingIdentity` unset, activation removes only a copy it stamped. `vestal` on `PATH` then runs the signed copy.
- **Phase 7 (track C): activation always runs `timeout 5 vestal reload`**, output discarded, errors ignored: `reload` never starts an instance.
- **Phase 7 (track C): the `tests` check runs the whole suite under nixpkgs' Swift**, listing the tests with a generated `LinuxMain.swift` (`nix/gen-linuxmain.py`; nixpkgs' Swift has no `libIndexStore` for discovery), against a copy of `libFoundation.so` whose `/usr/share/zoneinfo/` path points at nixpkgs' tzdata. The `hm-module` check evaluates the module against stub Home Manager options and runs the signing step with stubbed `codesign` and `launchctl`.
- **Found for the Linux phase (track C): nixpkgs' corelibs Foundation reads time zones only from `/usr/share/zoneinfo`**, which NixOS lacks: a Nix-built vestal on mantle gets nil `TimeZone`s and broken ISO 8601 parsing. Fix in phase 8 (`$TZDIR`/`/etc/zoneinfo` lookups in VestalCore, or a patched Foundation in `package.nix`).

- **Phase 5: the layout is worked out in VestalCore** (`DashboardLayout`, tested): `views.main.order` without keys that name no widget, widgets of an unknown type (logged once) and repeats (the first stays). The views switch over `WidgetKind`, so the switch is exhaustive. Only `main` is drawn.
- **Phase 5: spacing.** Each type keeps its top padding (system bar 28, media 20, agenda, systems, lists and weather 24, clock 0); the first entry of the layout gets none, even when it is hidden (the brief's rule; entries below keep theirs). A standalone `claudeUsage` widget is a status row like the system bar, with its padding (28).
- **Phase 5: `show` order and privacy.** Items draw left to right in `show` order; `privacy` is always the item at the right end, after the spacer, wherever it is in the list (CONFIG.md already said "drawn at the right end"), so `examples/full.json` is the old row. Unknown and repeated items are skipped; absent or empty still means every item in the old order. The privacy item needs both options, and `p` toggles the first bar in `order` that shows it; a bar with the options but without the item in `show` leaves `p` inert, since CONFIG.md ties the key to the item.
- **Phase 5: host keys.** Hosts come from every systemHealth widget in `order`, in order, the first entry of each name (the popups and health jobs go by name too). Usable explicit keys (one ASCII letter, not `p` or `i`) are claimed first, the first host naming a letter keeping it; the others get their first free letter as in phase 1. check-config walks widgets by key, so with a clash between two widgets its "already the key of" may name a different host than the one that wins. A duplicate host name inside one widget shows one row.
- **Phase 5: state per widget key, player or directory.** Weather, lists, agendas and privacy are kept per widget key; now playing per player name; Claude usage per projects directory; host health per host name. Two widgets on the same player or directory share one poll. The top-level entry animations follow the sum of list rows and the list of weather locations, which for one widget each are the old values.
- **Phase 5: `hideWhenOff: false`** keeps the media row while the player is off and shows the player's name there (subtle colour, no artist). The play button does nothing then (phase 5 review): play/pause, like the poll, runs its AppleScript only while the player runs, since a `tell application` for a mistyped name would bring up AppleScript's "Where is …?" chooser.
- **Phase 5: the player must be running before its script runs** (see "Unverified on macOS"). The AppleScript text itself moved to VestalCore (`MediaScript`) so its quoting is tested; the name only ever appears inside an escaped string literal (backslash, quote, line breaks and tab escaped).
- **Phase 5: `Palette.current` is a global** that `Color.accent` and the others read, set at launch before any view. The brief keeps `Color.accent` working; passing the palette through the SwiftUI environment would have rewritten every colour line of the moved code. Tokyo Night gained a `background` (#1a1b26, its editor background) for `theme.background: "none"`. Unknown palette names fall back in VestalCore (`ThemeConfig.paletteName`); check-config warns.
- **Phase 5: `theme.background`** maps to `ThemeConfig.Background` (`solid` is spelled `"none"` in the config, so no `.none` case clashes with `Optional.none`); an unknown value means `aurora`.
- **Phase 5: weather `units`** only picks the suffix (`°F` for `"imperial"`, else `°C`), as CONFIG.md documents; the value comes from `fields.temp` unconverted.
- **Phase 5: tickers only for what is shown.** The media ticker runs only with a media widget in the view, the Claude ticker only with a Claude item or widget; the clock, stats and network tickers always run (the agenda and weather read the clock too).
- **Phase 5: the invariant loop in TASKS uses `find`**, so the guard check covers `Sources/VestalMac/Widgets/`.

- **Phase 4: one scheduler, three kinds of job.** Sources (always), host health (`host:<name>`, visible-only) and tickers the platform registers (visible-only). Due means not running, allowed to run now, and its interval passed since it last started (sources) or ended (host health and tickers, since the review, so a hanging command or AppleScript never runs back to back, as 9c17bfc slept after each round); after an error, min(interval, 60s). One `Task.sleep` timer sleeps until the next due job; a finished job, `setVisible` and `apply` re-plan at once, which gives the stale-on-show refresh. The runtime takes `now`, a fetcher and a cache, so tests drive it with a fake clock; a runtime that isn't `start()`ed only runs what `startDueJobs()` starts.
- **Phase 4: which hosts get a health job.** Only `url` hosts without a `source`, in systemHealth widgets listed in `views.main.order` (polling hosts nobody sees wastes a process every 5s). A host with both `url` and `source` reads the source, as CONFIG.md says. A source-backed host is just its source: always-run, on the source's `refresh`, and its `interval` is unused (documented). An unknown `provider` gives the host an error snapshot and never runs `foyer-api`.
- **Phase 4: sources that can never run** (unknown type, `http` without a usable `url`, `command` without `argv`, `calendar` without a platform calendar, i.e. on Linux) get an error snapshot when the runtime starts and are never scheduled. Other errors retry. Errors are logged once per new message, not on every retry.
- **Phase 4: HTTP must answer 2xx, and every `json` source must parse** (TASKS only says commands must exit 0 and parse json validates). An error page or a proxy's HTML no longer replaces good cached data. A top-level JSON scalar counts as valid.
- **Phase 4: the disk cache records the source's definition** (sorted-keys JSON). If it changed between runs, the old data shows and the source fetches at once, instead of serving, say, the old weather location for 30 minutes. `apply` does the same for a changed source; removed sources are cancelled and dropped; unchanged ones keep their data and schedule. Old cache files without a definition are trusted. `fetchedAt` is when the fetch started, so the cadence is the same whether or not vestal restarts.
- **Phase 4: tickers.** Clock and network+privacy both align to whole seconds, so they land together and SwiftUI renders once a second. The clock, network and stats tickers start one interval after the model's synchronous first reads (a second CPU reading a few milliseconds after the first gave a noisy delta); media and Claude usage run at once. Volume was read at the start of the media tick, as the brief groups them; since the review it is read with the stats, so an AppleScript that hangs no longer holds it.
